## 0. 先统一三个概念

### A. Suspend 不是引擎 suspend

当前文档里的 `SUSPEND/RESUME` 容易被理解成“让推理引擎暂停”。

但集群化推理的引擎一直在服务其他 Agent/用户，**不可能为某个会话把整个引擎 suspend**。
所以：

- 不引入“引擎 suspend”；
- 不假设 vLLM-Ascend 有 request suspend API；
- Agent 调工具时，正常情况是**这次请求结束**，引擎继续服务别人；
- 要保留的是 **KV 生命周期**：`retain` / `offload` / `demote` / `evict`，不是引擎暂停。

建议把 `SUSPEND/RESUME` 改成：

```text
TOOL_CALL：请求结束/不再占用 GPU，SC 决定 KV retain/offload
TOOL_RETURN：新请求到达，按 KV 命中/加载/重算处理
```

`resume_ttft` 也应定义成：

> 工具返回后，新请求从到达到首 token 的时间；不是“引擎 resume 的时间”。

### B. “在线迁移”要分清是请求还是 KV

`在线迁移` 现在有两种可能：

1. **KV 迁移**：`copy/move/offload/promote`，我们已有；
2. **请求迁移**：把一条正在 decode 的请求连同 KV + 请求状态搬到另一个实例（Llumnix 类）。

第 2 种代价大、依赖引擎支持，**不是 KV Fabric 的核心能力**。
文档里应明确写“请求迁移归引擎/D8，KV Fabric 不做”，不要用“在线迁移”这种模糊说法。

### C. Operator bubble 的准确描述

不是“KV/网络让算子没活干”，而是：

> KV 传输和集合通信（尤其 MoE 的 dispatch/combine）共用超节点网络，KV 抢带宽，通信算子变慢，batch 等这一步。

指标名称可以保留 `operator_bubble_ratio`，但定义要写清是“通信算子被 KV 传输拖慢导致的等待”。

## 6. SSD / GPUDirect 核实结果

### SSD-1（DONE）Mooncake 是否有 GPUDirect / SCADA 类直连

- 当前文档结论：LOCAL_DISK 读经 host staging，不是 SSD→HBM 直连。
- 需要核实：
  - Mooncake 是否有 GPUDirect Storage / SCADA 类路径；
  - 是否只对 `DISK/DFS` 或特定后端生效；
  - A5/昇腾是否有对应直连能力。

核实结果：

- Mooncake TE 的 `NVMeoFTransport` 有 NVIDIA cuFile/GDS，能读进已注册 HBM；
- 但 Store `LOCAL_DISK` 不走这条，仍走 offload/staging；
- vLLM connector 没有 GDS 入口；
- A5/昇腾没有 GDS；
- `storage_backend.h` 的 GDS 是 future layout，不是实现。

结论：LOCAL_DISK 继续写 staging；A5 上 SSD 可以存 KV，但不能 SSD→HBM 零拷贝。
